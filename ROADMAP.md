### Phase 5 · Verify and close the ready batch

#### How to audit a batch

1. Collect accepted changes with passing host checks. Prepare the target fixture loaders once, include any required new inputs, and verify the combined affected render and fixed-source cases on `host`, `noble310` and `noble312`. Combine cases sharing the same target setup and count an existing focused result when its inputs and covered cases match. Use the local selector for covered families during iteration and include shared consumers for shared changes.
2. Before freezing a provider or runtime batch, replay the two-edition Ubuntu inventory when its inputs changed, reconcile reviewed numerical facts and fingerprints, validate both collections and pass the strict numerical gate. Check documentation links and refresh affected media against the reviewed behavior. Evidence-only or prose-only closures use the applicable evidence and documentation checks. For published releases, use their existing exact-package results while the tag and artifacts still match.
3. If the batch is a release candidate, set the version in shipping order and update the changelog before freezing. Freeze the combined source and record the target fixture identities. For a candidate, build twice, compare the outputs, and verify the first build and historical upgrade fixture before attaching them to the final runs. This lets the final matrix also cover the candidate's package tests. Run the applicable installed-prefix checks on the first build. [Versioning](docs/versioning.md#assigning-the-next-number) · [Exact-package verification](docs/release-candidate.md#final-source-and-package-checks)
4. Run one ordinary unsharded `bash tests/run.sh` offline per target on the frozen inputs. Record the discovered IDs, outcomes, skip reasons, exit code and timing as each target finishes. Close when all targets pass with the expected skips accounted for. On failure, reproduce with a focused check before repeating expensive work. Retain completed target evidence only when source, fixtures and relevant execution inputs still match. A changed shared snapshot needs the affected verification on the corrected inputs. [Command-help audit procedure](docs/development.md#auditing-command-help) · [Offline target setup](docs/test-selection-plan.md#reproduce-the-paired-offline-baseline)
